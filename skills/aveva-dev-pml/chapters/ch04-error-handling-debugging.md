# Chapter 4: Error Handling & Debugging

## Core Idea
AVEVA PML provides structured exception trapping via the `HANDLE ... ENDHANDLE` block attached immediately to executable commands. Custom domain errors are propagated using `RETURN ERROR`, while diagnostic tracing (`PML TRACE`, `ALPHA LOG`), system querying (`Q PML`), and DABACON transaction rollback (`MARK`, `UNDO`, `REDO`) provide deterministic control over execution and database state.

## Frameworks Introduced

### 1. AVEVA Error Specification Tuple
System errors are identified as a 2-part numeric tuple `(module_id, error_code)`:
* `module_id`: Numeric identifier of the originating AVEVA module (e.g., `41` for modeling/hierarchy violations, `1000` for .NET interop).
* `error_code`: Specific error reason (e.g., `8` for invalid hierarchy position, `12` for duplicate element name).

### 2. `HANDLE` Exception Trapping Pipeline
* `HANDLE` is a **post-attached trap**, not a block wrapper: the risky command comes FIRST, and the `handle ... endhandle` clause follows IMMEDIATELY after it with no intervening statements. The statements between `handle` and `endhandle` are the **recovery code** that runs only when the preceding command fails — they are NOT the guarded code.
* Never place the risky command inside `handle ... endhandle`. There is no `try`/`catch` in PML; thinking of `handle` as a try-block produces code where the real command only runs on the error path.
* Supports targeted error matching `HANDLE (mod, code)`, chained `ELSEHANDLE (mod, code)`, catch-all `ELSEHANDLE ANY`, and success branching `ELSEHANDLE NONE`.

### 3. Exception Propagation (`RETURN ERROR`)
* Halts current method or function and raises an error to caller: `return error <num> '<message>' [noalert]`.
* The `noalert` keyword prevents AVEVA from displaying a standard modal popup error dialog, enabling silent programmatic handling.

### 4. DABACON Transaction Rollback Framework (TM-2263 Chapter 17.2)
When modifying model geometry or attributes in Design, unexpected script failures can leave databases in inconsistent states. AVEVA provides transaction save points:
* **`MARK '<savepoint_name>'`**: Sets a named checkpoint in the current database session.
* **`UNDO`**: Rolls back database changes made since the last `MARK`.
* **`REDO`**: Re-applies the changes rolled back by `UNDO`.
* **`Q MARKS`**: Queries all active transaction marks in the current session.

### 5. Runtime Diagnostic & Query Suite (SOFTCG Chapter 12 & TM-2263)
* **Tracing**:
  * `PML TRACE ON` / `PML TRACE OFF` (or `TRACE ON` / `TRACE OFF` in macros).
  * Fine-grained flags: `pml trace lines`, `pml trace vars`, `pml trace commands`.
* **Session Logging**:
  * `ALPHA LOG /C:\temp\session.log OVERWRITE` records all command window activity and PML trace output directly to a disk file.
  * `ALPHA LOG END` closes the log file.
* **PML Environment Query Commands (`Q PML` & `$Q`)**:
  * `Q PML FNC <function_name>`: Displays definition path and signature of a function.
  * `Q PML FORMS`: Lists all loaded forms in the session.
  * `Q PML MODS`: Lists all loaded modules and assemblies.
  * **`$Q syserror` (TM-2263 Chapter 17.3)**: Queries and displays the last system error code and detailed message generated by the engine.
* **Database Snapshot Marking & Rollback (TM-2263 Chapter 17.2)**:
  * `MARK '<tag>'`: Places a named checkpoint in the DABACON session.
  * `UNDO TO '<tag>'`: Reverts database modifications back to the named checkpoint.
  * `REDO`: Re-applies changes that were rolled back via UNDO.
* **Source File Encoding (Unicode Rules)**:
  * PML 2 files containing extended characters must be saved in **UTF-8 with BOM (Byte Order Mark)**. Files without BOM will misinterpret multibyte characters.

## Key Concepts
* **`HANDLE`**: Block attached immediately to an error-prone command to intercept failures.
* **`ELSEHANDLE ANY`**: Universal fallback catching any unexpected runtime error.
* **`ELSEHANDLE NONE`**: Block executed exclusively when the guarded statement succeeds without error.
* **`!!ALERT`**: Pre-instantiated global system object providing modal dialogs:
  * `!!Alert.Message(|text|)`, `!!Alert.Warning(|text|)`, `!!Alert.Error(|text|)`.
  * `!ans = !!Alert.Confirm(|text|)`, `!ans = !!Alert.Question(|text|)`, `!val = !!Alert.Input(|prompt|, |default|)`.

## Code Examples

### Structured Error Trapping and Transaction Rollback
```pml
-- ================================================================
-- Example: Safe Database Transaction with Error Rollback
-- ================================================================

-- 1. Create Transaction Mark
MARK 'BEFORE_EQUIPMENT_CREATION'

NEW EQUI /VESSEL-101
HANDLE (41, 8)
  $P Warning: Current element is not a ZONE. Navigating to default ZONE...
  /ZONE-EQUIPMENT-DEFAULT
  NEW EQUI /VESSEL-101
ELSEHANDLE (41, 12)
  $P Error: Equipment name /VESSEL-101 already exists in DABACON database.
  -- Revert any partial changes back to mark
  UNDO
  return error 101 'Duplicate Equipment Name' noalert
ELSEHANDLE ANY
  $P Unexpected error during EQUI creation. Rolling back transaction...
  -- Safe rollback
  UNDO
  return error 100 'Failed to create Equipment /VESSEL-101' noalert
ELSEHANDLE NONE
  $P Success: EQUI /VESSEL-101 created successfully.
ENDHANDLE

-- 2. Interactive user confirmation via !!ALERT
!choice = !!Alert.Confirm(|Do you want to delete the selected nozzle?|)
if (!choice EQ 'YES') then
  DELETE $!ce
  $P Element deleted.
else
  $P Deletion cancelled by user.
endif
```

## Anti-patterns
* **Using `try / catch` or `throw`**: Modern keywords like `try`, `catch`, and `throw` do not exist in PML; using them causes syntax errors.
* **Writing the risky command INSIDE `handle ... endhandle`** (the try/catch mistake): The guard traps the command written *before* it, not the commands written inside it. Putting the real work inside the trap means it only runs on the error path, and the failure you wanted to catch is never caught.
  ```pml
  -- WRONG: assignment misplaced into the recovery block
  handle any
    !modelNo = !elem.:SPEC
  endhandle

  -- CORRECT: risky command first, recovery code in the trap
  !modelNo = !elem.:SPEC
  handle any
    !modelNo = ''
  endhandle
  ```
* **Placing `HANDLE` detached from the failing command**: Placing intervening statements between the risky command and its `HANDLE` will cause the error to bubble up uncaught, aborting execution.
* **Silently absorbing errors with empty `HANDLE ANY`**: Never write an empty `HANDLE ANY` without at least logging the condition via `$P` or status message `$S`.
* **Performing Major Batch Edits Without `MARK`**: Modifying hundreds of elements without periodic `MARK` checkpoints prevents clean rollback on crash.

## Reference Tables
| Alert / Diagnostic Command | Syntax / Method | Return / Behavior |
|---|---|---|
| Informational Alert | `!!Alert.Message(text)` | Modal dialog with OK button |
| Confirmation Alert | `!!Alert.Confirm(text)` | Returns `'YES'` or `'NO'` |
| Question Alert | `!!Alert.Question(text)` | Returns `'YES'`, `'NO'`, or `'CANCEL'` |
| User Input Alert | `!!Alert.Input(prompt, def)` | Returns string, or unset if cancelled |
| Transaction Checkpoint | `MARK '<name>'` | Sets savepoint in DABACON session |
| Undo Transaction | `UNDO` | Reverts DB changes to previous mark |
| Redo Transaction | `REDO` | Re-applies undone DB changes |
| Query PML Function | `Q PML FNC <name>` | Prints source path and argument types |
| Alpha Session Log | `ALPHA LOG <path> OVERWRITE` | Directs command terminal log to file |

## Key Takeaways
1. AVEVA PML handles errors using `HANDLE ... ELSEHANDLE ... ENDHANDLE`, NOT `try/catch`.
2. `HANDLE` must immediately follow the command that may fail — it trails (post-attaches to) the guarded command and never encloses it; the guarded command goes BEFORE the trap, the recovery code goes inside it.
3. Guard complex database mutations with `MARK '<name>'` and `UNDO` rollback handlers.
4. Diagnose runtime issues with `PML TRACE ON`, `ALPHA LOG`, and `Q PML` query commands.
